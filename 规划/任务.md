# LangChain 生成层下一阶段任务清单

## 当前状态

当前项目已经完成检索主链路，且业务入口已经切换到 LangChain 版本。
后续工作重点不再是继续堆检索能力，而是把“检索结果 -> Prompt -> 回答生成 -> 引用展示 -> 拒答策略”这一整段生成链路做稳。

当前主要文件：
- `core/service/rag_langchain_native.py`
- `core/service/langchain_adapters.py`
- `core/service/rag_grounding.py`

---

## 总目标

下一阶段的目标是把当前 LangChain RAG 从“能回答”升级到“回答稳定、引用可靠、拒答清晰、结构自然”。

要解决的核心问题：
1. 检索到了内容，但 Prompt 组织还不够稳定
2. 多个 chunk 命中时，回答整合还不够自然
3. strict_mode / 无证据 / 弱证据场景下，拒答策略还不够统一
4. 引用存在兜底，但还没有和回答风格做更细致协同
5. 生成层还缺少针对 yes_no / list / how_to / frequency 的差异化回答模板

---

## 阶段 1：先做 Prompt 与上下文组织

### 目标
让模型“更容易用好检索结果”，减少答偏、答散、答空泛。

### 主要文件
- `core/service/rag_langchain_native.py`

### 重点函数
- `format_documents_as_context(...)`
- `build_langchain_rag_prompt(...)`
- `build_answer_instruction(...)`

### 要做的事
1. 统一 context 结构
   - 明确每个 chunk 的展示格式
   - 固定顺序：来源头 -> 正文 -> 空行
   - 评估是否要把 `score / page / source_section` 更清晰地表达给模型

2. 控制上下文噪声
   - 避免 chunk 头信息过长，影响模型注意力
   - 保留必要来源信息，不把 prompt 塞得太重
   - 若后续 context 太长，预留截断策略

3. 统一回答要求
   - 有 context 时：必须优先依据知识库回答
   - 无 context 且 strict_mode=True：直接拒答
   - 无 context 且 strict_mode=False：允许补充，但必须声明不是知识库内容

### 完成标准
- prompt 结构固定
- context 表达清晰
- strict / non-strict 指令边界明确

---

## 阶段 2：做 grounding 与拒答策略

### 目标
减少幻觉，让“该答就答、该拒就拒”。

### 主要文件
- `core/service/rag_langchain_native.py`
- `core/service/rag_grounding.py`

### 重点函数
- `build_direct_grounded_answer(...)`
- `evidence_match_score(...)`
- `relation_evidence_score(...)`
- `stream_answer_with_knowledge_langchain_native(...)`

### 要做的事
1. 强化 direct grounded answer 的使用边界
   - 证据足够强时，优先直接返回
   - 证据不够时，再交给 LLM 生成

2. 统一拒答策略
   - 无 context + strict_mode=True：固定拒答
   - 有 context 但 evidence 很弱：保守回答或提示“知识库未明确提及”
   - chunk 之间冲突时：优先保守表达，不做强结论

3. 让关系证据真正参与生成前决策
   - 对 yes_no 类问题，不能只看主题接近
   - 要结合 `relation_evidence_score(...)` 判断是否适合给确定性结论

### 完成标准
- strict_mode 下不乱答
- 有直接证据时优先走 grounded answer
- 模型生成前的分流逻辑更稳定

---

## 阶段 3：做 answer synthesis

### 目标
让最终回答更像“整理后的答案”，而不是“把检索文本复述一遍”。

### 主要文件
- `core/service/rag_langchain_native.py`
- `core/service/rag_grounding.py`

### 重点函数
- `build_answer_instruction(...)`
- `stream_answer_with_knowledge_langchain_native(...)`
- `build_direct_grounded_answer(...)`

### 要做的事
1. 按问题类型区分回答风格
   - `yes_no`：先给结论，再给证据
   - `list`：优先列点或列项
   - `how_to`：优先步骤化
   - `frequency`：优先给周期/频率结论
   - `fact`：先给定义或结论，再补充细节

2. 优化多 chunk 整合方式
   - 多个 chunk 命中时，要求模型先合并再回答
   - 避免重复表述
   - 避免把多个来源机械堆叠

3. 统一输出风格
   - 回答先结论、后解释
   - 尽量短句清晰
   - 知识库未明确提到的内容要单独声明

### 完成标准
- yes_no / list / how_to 等常见问题输出风格明显改善
- 多 chunk 命中时答案更自然
- 结构更稳定，不容易跑偏

---

## 阶段 4：做引用与答案协同

### 目标
让引用不仅“存在”，而且“和答案对得上”。

### 主要文件
- `core/service/rag_langchain_native.py`

### 重点函数
- `build_citations_from_documents(...)`
- `ensure_answer_has_document_citations(...)`
- `_build_reference_line(...)`

### 要做的事
1. 检查引用兜底是否过于粗粒度
   - 现在是答案末尾统一追加“参考来源”
   - 后续可以评估是否要让 inline citation 更一致

2. 保持用户可读性
   - PDF 的 `page_6` 这种内部标识不要暴露给用户
   - 引用行尽量统一、简洁、可读

3. 处理重复引用
   - 同文档同页去重
   - 同答案多 chunk 命中时避免重复列出一堆几乎一样的来源

### 完成标准
- 引用块整洁
- 不暴露内部结构化占位符
- 引用和回答表达风格统一

## 阶段 5：清理与统一 LangChain 代码

### 目标
把当前只保留 LangChain 的架构收口，避免后续维护混乱。

### 主要文件
- `core/service/rag_langchain_native.py`
- `core/service/langchain_adapters.py`

### 要做的事
1. 清理旧注释
   - 删除“和手写版并存”的历史表述
   - 统一改成当前 LangChain-only 架构说明

2. 清理乱码 / 临时注释
   - 例如 `Step 4????????` 这类中间调试痕迹需要删掉
   - 保证代码可读性

3. 统一命名和职责边界
   - `rag_langchain_native.py` 负责生成链
   - `langchain_adapters.py` 负责适配层
   - `rag_grounding.py` 负责证据与规则判断

### 完成标准
- 架构说明一致
- 注释不误导
- 文件职责清晰

## 阶段 6：最后补评估闭环

### 目标
让你后续优化生成层时，不再只靠感觉。

### 建议先做的最小评估集
1. yes_no 类
   - 例：是否支持某功能
2. list 类
   - 例：有哪些语音助手 / 有哪些模式
3. how_to 类
   - 例：怎么设置 / 怎么连接
4. frequency 类
   - 例：多久清理一次
5. fact 类
   - 例：某功能是什么 / 某参数含义是什么

### 每类至少记录
- 一个正常命中 case
- 一个弱证据 case
- 一个容易幻觉 case
- 一个检索到了但生成不好的 case

### 判断维度
- 是否答非所问
- 是否幻觉
- 是否该拒答却没拒
- 是否引用不清晰
- 是否多 chunk 整合很乱

---

## 推荐执行顺序

1. 先改 `rag_langchain_native.py` 的 prompt 与 context 组织
2. 再补 `rag_grounding.py` 的生成前分流与拒答判断
3. 再做按问题类型区分的 answer synthesis
4. 然后优化引用协同
5. 最后清理 LangChain 注释和补评估集
