#### 缺口1：Cross-Encoder Reranker 模型精排

**当前问题**：
- 现有rerank是**规则融合**（证据分+关系分+短语重叠），能排掉约30%噪声
- 对"语义相关但字面不匹配"的排序能力弱

**需要学习的技术知识点**：

| 知识点 | 学习内容 | 为什么重要 |
|-------|---------|-----------|
| **Bi-Encoder vs Cross-Encoder 区别** | Bi-Encoder：query和doc分别编码→向量相似度<br>Cross-Encoder：query+doc拼接后一起编码→直接打分 | Cross-Encoder精度高20-30%，适合精排阶段 |
| **bge-reranker 系列** | - bge-reranker-base（中文通用）<br>- bge-reranker-large（精度更高）<br>- bge-reranker-v2-m3（多语言） | 目前中文RAG领域效果最好的reranker之一 |
| **jina-reranker** | jinaai/jina-reranker-v1-base-zh | 另一个高性能选择，可做对比实验 |
| **sentence-transformers CrossEncoder** | API用法：`CrossEncoder(model_name).predict([[query, doc1], [query, doc2]])` | 标准调用方式，兼容大多数reranker模型 |
| **RRF 倒数秩融合** | Reciprocal Rank Fusion：不依赖分数，只用排名 | 当不同召回路分数不可比时，RRF比加权融合更鲁棒 |
| **分数融合策略** | - 加权求和（已有）<br>- RRF倒数秩融合<br>- CombSUM / CombMNZ | 多路召回结果的融合方法论 |

**具体落地任务**：

3. [ ] 实现 CrossEncoder 批量打分接口

#### 缺口4：ANN近似最近邻索引升级

**当前问题**：
- FAISS只用了 IndexFlatIP（暴力精确搜索），O(N)复杂度
- 单用户chunk超过5万条后，搜索延迟会从毫秒级升到秒级

**需要学习的技术知识点**：

| 知识点 | 学习内容 | 为什么重要 |
|-------|---------|-----------|
| **暴力搜索 vs ANN 搜索** | Flat=精确O(N)，ANN=近似O(logN)，精度换速度 | 10万条以上必须上ANN |
| **IVF倒排文件索引** | - 聚类：K-means把向量分成nlist个桶<br>- 搜索：先找最近的几个桶，桶内精搜 | 最基础的ANN索引，原理易懂 |
| **HNSW层次化小世界图** | 多层近邻图结构，从粗到细搜索 | 目前最主流的ANN索引，精度/速度平衡最好 |
| **PQ乘积量化** | 向量压缩技术，100万向量也能存进内存 | 超大规模时的内存优化 |
| **FAISS Index Factory** | 用字符串配置索引：`"HNSW64"` / `"IVF4096,PQ64"` | 快速组合不同索引结构 |
| **索引构建流程** | 训练(Train)→添加(Add)→保存(Save) | IVF类索引需要先"训练"再用，Flat不用 |

#### 缺口7：RAG评测体系

**当前问题**：
- 改完任何参数/策略，只能靠"感觉效果好了"，无法量化
- 改了rerank权重，不知道是变好还是变坏
- 没有基线（baseline）对比，无法证明迭代有效

**需要学习的技术知识点**：

| 知识点 | 学习内容 | 为什么重要 |
|-------|---------|-----------|
| **Recall@K** | 正确答案在前K条结果里出现的比例 | **最核心的检索指标**，K=5/10/20 |
| **MRR 平均倒数排名** | Mean Reciprocal Rank：第一个正确结果排名的倒数的平均 | 关注"排第一的是不是对的" |
| **NDCG** | Normalized Discounted Cumulative Gain | 考虑所有正确结果的位置，排名越靠前权重越高 |
| **Faithfulness 忠实度** | 回答内容是否都有上下文支撑，有没有"幻觉" | 生成质量的核心指标 |
| **Context Precision** | 给LLM的上下文，是不是越靠前越相关 | 上下文排序质量 |
| **Citation Correctness** | 每条引用是不是真的支撑了对应回答 | 引用可信度 |
| **人工评测集设计** | 20-50条标准问题，覆盖yes_no/how_to/list/frequency/fact | 保证评测多样性 |
| **Ragas 评测框架** | 开源RAG评测工具，Faithfulness/Context Precision等开箱即用 | 不用从零写评测代码 |

- 当前FAISS是**单文件单用户索引**架构
- 局限性：
  - 多服务部署时，索引文件不共享
  - 增量更新不方便（每次全量重建）
  - 不支持Metadata原生过滤
  - 数据量超100万条后性能瓶颈

**需要学习的技术知识点**：

| 知识点 | 学习内容 | 为什么重要 |
|-------|---------|-----------|
| **pgvector** | PostgreSQL的向量扩展，向量+关系数据存一起 | **最推荐的升级路径**，和现有数据架构最兼容 |
| **pgvector 索引类型** | ivfflat / hnsw 两种pgvector索引 | 和FAISS类似的ANN原理 |
| **Milvus / Qdrant** | 专业分布式向量数据库 | 超大规模（亿级）时才需要 |
| **向量相似度操作符** | pgvector: `<=>` L2距离, `<#>` 内积, `<=>` 余弦 | SQL原生支持向量查询 |

**具体落地任务**（建议先做pgvector试点）：
1. [ ] 数据库安装 pgvector 扩展：`CREATE EXTENSION vector;`
2. [ ] KnowledgeChunks 表加向量列：
   ```sql
   ALTER TABLE knowledge_chunks ADD COLUMN embedding vector(1536);
   CREATE INDEX ON knowledge_chunks USING hnsw (embedding vector_cosine_ops);
   ```
3. [ ] 实现向量查询：
   ```python
   # SQLAlchemy 原生查询
   stmt = (
       select(KnowledgeChunks)
       .filter(KnowledgeChunks.user_id == user_id)
       .order_by(KnowledgeChunks.embedding.cosine_distance(query_vec))
       .limit(top_k)
   )
   ```
4. [ ] 对比测试：pgvector vs FAISS 的延迟+精度
5. [ ] 混合检索改造：BM25（PostgreSQL full-text search）+ pgvector 向量检索

## 五、暂时不用急的技术（避坑指南）

| 技术方向 | 为什么先不学 | 什么时候再学 |
|---------|-------------|-------------|
| **Agent / LangGraph / Function Calling** | 当前项目主线是知识库问答，不是多工具Agent | 基础RAG的Recall@5稳定>80%之后 |
| **多模态RAG（图片/视频理解）** | 文本RAG的召回还没做到极致 | 文本评测稳定后，有图片场景需求时 |
| **Graph RAG + 知识图谱** | 门槛高，投入产出比低，100万token以下文本不如分块RAG | 文档规模超10万页，需要跨文档推理时 |
| **Milvus 分布式向量库** | 单机pgvector/FAISS足够支撑百万级 | 多服务共享索引、单库超亿级向量时 |
| **混合大模型（MoE）/ 推理优化** | 不是你的瓶颈，当前瓶颈在检索不在生成 | 生成延迟成主要矛盾时 |
