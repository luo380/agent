# 口语化问法检索优化学习笔记

## 一、这次遇到的问题是什么

这次遇到的不是“知识库里没有答案”，也不是“文档没有做向量化”，而是：

- 知识库里明明已经有相关内容
- 正确 chunk 也已经成功入库
- 但是用户换成口语化问法之后，系统没有把最相关的 chunk 排到前面

典型例子：

用户提问：

`我家里有小爱同学，不知道可以控扫地机器人吗`

知识库中已有内容：

`常见的有小爱同学、天猫精灵、Google Assistant 等。`

错误现象：

- 系统没有优先命中“支持哪些语音助手”这段内容
- 反而更容易回答成“扫地机器人一般怎么操作”“机器人通常通过 APP 或按键操作”这类泛内容

所以本质问题不是“没有知识”，而是“问题没被检索层正确理解”。

---

## 二、什么是口语化问法

口语化问法，就是更像人在聊天时自然说出来的话，而不是为了给搜索系统或 FAQ 写的标准问题。

同一个意思，可以有三种表达：

1. 口语化：
   `我家里有小爱同学，不知道能不能控扫地机器人`
2. 书面化：
   `我想了解扫地机器人是否可以通过小爱同学进行控制。`
3. 标准问法：
   `扫地机器人是否支持小爱同学语音控制`

口语化表达的特点：

- 会带铺垫词，比如：`我家里有`、`我想问下`、`不知道`
- 会用短词、俗称、简称，比如：`控` 代替 `控制`
- 语序更自由，不一定严格按“主语 + 谓语 + 宾语”组织
- 真正重要的实体，可能被夹在一大段自然语言中间

这会导致检索层很难第一时间抓住真正重要的词。

---

## 三、这次问题为什么会发生

原来的检索逻辑更擅长处理标准问法，比如：

- `支持什么语音助手`
- `扫地机器人是否支持小爱同学`
- `天猫精灵能否控制扫地机器人`

但它不太擅长处理下面这种更自然的口语表达：

- `我家里有小爱同学，不知道可以控扫地机器人吗`

原因在于：

1. 问句里有很多“弱语义词”
   - `我家里有`
   - `不知道`
   - `可以`
   - `控`

2. 真正有价值的实体没有被稳定抽出来
   - `小爱同学`
   - `扫地机器人`

3. recall 和 rerank 更多还是在利用整句、尾部焦点、常规 query form

于是会出现一种情况：

- 向量有
- 正确 chunk 有
- 但 query 没拆好
- 所以召回和重排偏了

---

## 四、这次修改解决的是什么层级的问题

这次修改解决的是：

`口语化但仍然带有明显实体和明显意图词的问题`

比如：

- `我家里有X，不知道可不可以控Y`
- `我有X，能不能控制Y`
- `请问X能不能用在Y上`

这里的核心不是适配某个固定品牌词，而是增强这类句式的理解能力。

也就是说，这次不是单独为：

- `小爱同学`
- `扫地机器人`

写死逻辑，而是增强了：

- 口语 yes/no 问法识别
- 控制类关系识别
- 前半句和后半句实体抽取

---

## 五、这次具体改了什么

本次改动主要在下面两个文件中：

- `core/service/rag_grounding.py`
- `core/service/retrieval.py`

并补充了测试：

- `test/test_retrieval.py`

### 1. 扩展 yes/no 类锚点

原来系统主要识别：

- `是否支持`
- `能否支持`
- `支持`
- `兼容`

这次新增了更贴近日常说法的锚点：

- `能不能`
- `可不可以`
- `能否`
- `可以`
- `控不控`
- `能控`
- `可以控`
- `控制`

作用：

让系统把“能不能控”“可不可以用”这种自然表达，也识别成 yes/no 或控制类问题。

### 2. 扩展动作前缀

新增了：

- `控制`
- `控`

作用：

当系统抽词时，不再把“控扫地机器人”整体当成模糊文本，而是更容易识别：

- `控` 是动作词
- `扫地机器人` 才是实体目标

### 3. 新增口语前缀清洗

新增清洗这类前缀：

- `我家里有`
- `家里有`
- `我这边有`
- `我有`
- `现在用的是`
- `我用的是`
- `我用`

作用：

把口语中的“上下文铺垫”去掉，让实体更容易显露出来。

### 4. 新增口语填充词清洗

新增清洗：

- `不知道`
- `想知道`
- `请问`
- `问下`
- `问一下`
- `麻烦问下`
- `麻烦`

作用：

减少礼貌词、犹豫词、铺垫词对 query 的干扰。

### 5. 支持分句抽取焦点词

这次不再只依赖：

- 锚点后的尾部文本

而是会对整句按中文标点分片，例如：

`我家里有小爱同学，不知道可以控扫地机器人吗`

会被拆成：

- `我家里有小爱同学`
- `不知道可以控扫地机器人吗`

然后分别抽词。

作用：

可以同时得到：

- 前半句实体：`小爱同学`
- 后半句目标：`扫地机器人`

### 6. 把 grounding 抽出的焦点词重新喂回 recall

在 `build_recall_query_forms(...)` 中，把 `extract_question_focus_terms(...)` 抽出来的词加入 recall forms。

作用：

让这些明确的焦点词直接参与：

- query expansion
- recall
- rerank

这一步很关键，因为它把“抽词”真正接到了“检索”上，而不只是留在分析层。

---

## 六、这次修改后的收益

修改后，系统不再只依赖“整句语义相似度”去判断答案，而是多了一层显式实体信号。

对于下面这类句式会更稳：

- `我家里有X，不知道可不可以控Y`
- `我有X，能不能控制Y`
- `请问X能用在Y上吗`

这意味着：

- 更容易命中正确实体所在的 chunk
- 更不容易被“泛操作说明类 chunk”抢走排序前列

---

## 七、这次不是在做什么

这次不是：

- 重新训练 embedding 模型
- 修改向量维度
- 替换向量数据库
- 重做 chunking

也不是简单地“给小爱同学加特判”。

这次做的是：

`增强 query understanding，让检索层更懂中文口语问法`

---

## 八、它现在还不完全适合什么问题

这次增强以后，系统更擅长“口语化显式问法”，但还不完全适合下面这些更复杂的问题：

### 1. 特别绕的长句

比如一整句话里有很多修饰、很多背景信息、多个条件，真正的问题主干很难直接抽出来。

需要后续继续提升：

- 长句压缩
- 主干抽取
- query rewrite

### 2. 多层关系推理

比如一句话里不只是“X 能不能控 Y”，而是：

- X 通过什么方式控制 Y
- Y 的哪个功能支持 X
- 在什么条件下支持或不支持

这类问题需要更强的关系建模，而不只是抽关键词。

### 3. 没有明显锚点的隐式问法

例如用户没有直接说：

- `支持`
- `控制`
- `兼容`

而是换成隐含表达。

这种问题不能只靠规则词，还需要更强的语义理解。

### 4. 非常自由的口语表达

比如：

- 省略严重
- 主谓宾顺序很乱
- 有多层跳跃表达

这类问题未来可能需要：

- 更强的 query rewrite
- 小模型意图抽取
- LLM 先改写问题再检索

---

## 九、这是不是以后要继续解决的问题

是的。

可以把整个演进过程理解成四层：

1. 先解决标准问法
2. 再解决常见口语化问法
3. 再解决复杂自然语言问法
4. 最后解决隐式表达和多层关系推理

这次完成的是第 2 层中的一部分：

`口语化显式问法增强`

后续还要继续补的是：

- 复杂句理解
- 隐式问法识别
- 多层关系推理
- query rewrite

## 十、这次我学到了什么

### 1. RAG 出错不一定是“没有向量”

很多时候向量是有的，正确 chunk 也是有的，真正的问题是：

- query 没理解好
- recall 没召回好
- rerank 没排好

### 2. 用户真实提问通常不是标准问法

在真实业务里，用户更常说的是聊天语言，而不是 FAQ 语言。

所以如果只优化标准问法，系统一上线就会遇到很多“知识明明有，但答不准”的情况。

### 3. grounding 不只是回答阶段有用

grounding 里的焦点词抽取能力，也可以反过来帮助 recall 和 rerank。

这说明：

`回答前的理解能力，可以直接增强检索能力`

### 4. 规则增强是很好的第一步

这次方案不是最强的语义理解方案，但它有几个优点：

- 改动成本低
- 落地快
- 见效直接
- 特别适合先补中文口语问法的坑

所以在项目演进里，这是很有价值的一步。

## 十二、一句话总结

这次优化的本质不是“补向量”，而是：

`让口语化问题里的关键实体，能被检索层正确看见。`

如果继续往后做，下一阶段应该从“口语化显式问法增强”继续升级到：

- 更强的 query rewrite
- 更复杂的关系理解
- 更自然语言化的检索改写能力
