## 当前代码里已经完成的内容

### 1. 查询扩展：已开始

当前项目在检索层已经不是只拿“用户原问题”直接去搜，而是开始对 query 做扩展和变形。

相关代码位置：

- `core/service/retrieval.py`
- 关键函数：
  - `build_recall_query_forms(...)`
  - `_phrase_query_forms(...)`
  - `coarse_recall_score(...)`
  - `rerank_chunks(...)`

当前已经做了什么：

- 会保留原始问题作为主查询
- 会尝试抽取问题中的焦点尾部
- 会对中文查询做短语/词片段扩展
- 会在召回和 rerank 阶段同时利用这些 query forms

这说明我已经开始学习“查询扩展”这件事，而不是停留在最基础的“一个 query 只搜一次”。

可以这样理解：

- 原始做法：`用户问题 -> 向量检索`
- 当前做法：`用户问题 -> 生成多个 query form -> 参与召回和重排`

这已经属于第 3 周内容里的“高级检索思路”。

---

### 2. 检索优化：已明显完成一大部分

当前项目最核心的进展，是 `search_similar_chunks(...)` 这一层已经不再是早期的单纯向量检索。

相关代码位置：

- `core/service/retrieval.py`
- `core/service/vector_index.py`

当前已经具备的能力：

- FAISS 向量检索
- BM25 关键词检索
- 分数归一化
- Hybrid Search 混合召回
- Rerank 精排

检索流程大致已经变成：

1. 用户问题生成 embedding
2. 走 FAISS 做语义召回
3. 走 BM25 做关键词召回
4. 把两路结果做分数归一化
5. 合并、去重、加权
6. 再走 `rerank_chunks(...)`
7. 选出最适合拼接到 context 的候选块

这说明我在第 3 周里“优化检索函数”这件事已经做得比较深入了。

如果从学习阶段来讲，这已经不只是“会用向量检索”，而是开始理解：

- 为什么只靠向量检索不够
- 为什么要混合关键词检索
- 为什么要做召回和精排分层
- 为什么不同分数源要先归一化再融合

### 3. 结构化分块：已做，但不等于语义分块

当前项目在分块层已经比最早的固定窗口切分更好一些，但还不能直接算“语义分块”。

相关代码位置：

- `core/service/chunking.py`
- 关键函数：
  - `chunk_text(...)`
  - `chunk_parsed_document(...)`
  - `_chunk_single_text(...)`

当前已经做了什么：

- 优先按 `pages` 切块
- 其次按 `sections` 切块
- 如果没有结构信息，再回退到固定长度切块
- 使用 `chunk_size + overlap`
- 保留 `source_page`、`source_section`、`offset`

这属于“结构化分块”或“规则分块”，优点是：

- 比纯长度切块更有来源感
- 便于引用页码、章节
- 更适合后续做 citations

但它还不等于“语义分块”。

因为真正的语义分块更关注：

- 语义是否完整
- 一段内容是否讲同一件事
- 是否在自然边界处分割
- 是否避免把一个完整答案硬切成两半

所以这部分当前状态应该记为：

- 已有基础分块能力
- 还没实现真正的 semantic chunking

---

### 4. 上下文压缩：只做了弱化版

当前项目已经在一定程度上控制了上下文长度，但这还不属于完整的 context compression。

相关代码位置：

- `core/service/retrieval.py`
- `core/service/rag.py`
- 关键函数：
  - `search_similar_chunks(...)`
  - `rerank_chunks(...)`
  - `build_context(...)`

当前做法主要是：

- 先召回较多候选
- 再 rerank
- 最后只取 `top_k`
- 再把这些 chunk 直接拼接进 `context`

这个过程确实起到了“缩小输入范围”的作用，但它本质上还是：

- 候选筛选
- Top-K 控制

而不是严格意义上的“上下文压缩”。

真正的上下文压缩通常还会继续做这些事情：

- 只截取 chunk 中最相关的句子
- 对长 chunk 做局部摘要
- 去掉重复信息
- 在保留证据的前提下减少 token

所以这一项当前更准确的判断是：

- 已经有“上下文控制”
- 还没有“真正的上下文压缩”

## 当前最适合继续补的两项能力

### 1. 语义分块

下一步最值得补的是：不要只按固定长度和结构字段切块，而是尝试按语义边界切块。

目标：

- 同一 chunk 尽量只表达一个主题
- 减少答案跨 chunk 断裂
- 提高召回后 chunk 的可读性和可回答性

可以考虑的方向：

- 先按段落切，再按语义相近度合并
- 利用标题、列表、表格边界做切分
- 为中文文本加入句号、分号、换行等边界策略

---

### 2. 上下文压缩

下一步第二个重点是：不要把 rerank 后的 chunk 原封不动全部塞进 prompt，而是先压缩。

目标：

- 降低 token 消耗
- 减少噪音
- 提高回答聚焦度

可以考虑的方向：

- 只抽取 chunk 中命中 query 的关键句
- 对每个 chunk 先做 evidence snippet 提取
- 去掉多 chunk 之间重复表达的内容
- 超长 context 时先做一轮 summary compression
